# Architecture

## Crate structure

Khora is a 3-crate Rust workspace:

```
khora/
├── crates/
│   ├── khora-core/     # Types, config, errors, output formatting
│   ├── khora-cdp/      # Chrome discovery, CDP client, session lifecycle
│   └── khora-cli/      # clap commands, JSON output, entry point
```

### khora-core

Platform-agnostic types shared by all crates:

- `error.rs` — `KhoraError` enum with exit codes (thiserror)
- `config.rs` — `KhoraConfig`, currently used only for `sessions_dir()`. Its `~/.khora/config.json` loader is not wired into any command: timeouts come solely from `--timeout`/`KHORA_TIMEOUT` and format from `--format`/`KHORA_FORMAT`.
- `element.rs` — `ElementInfo`, `BoundingBox`, `NetworkRequest`, `ConsoleMessage`
- `session.rs` — `SessionInfo` with save/load/remove/list operations
- `output.rs` — `OutputFormat` enum (Text/Json), formatting functions

### khora-cdp

Chrome DevTools Protocol integration:

- `chrome.rs` — Chrome binary discovery per platform (macOS, Linux, Windows)
- `client.rs` — `CdpClient` wrapping chromiumoxide `Browser`; per-launch user data dir + cleanup
- `session.rs` — Process liveness check (`is_process_alive`), `load_and_verify`, `reap_stale_sessions` (called automatically at CLI startup)

### khora-cli

CLI entry point:

- `main.rs` — clap Parser/Subcommand, dispatches to CdpClient methods
- `build.rs` — stamps `KHORA_BUILD_VERSION` (read by `main.rs`'s `#[command(version = ...)]`) from `git describe --tags --always --long`, so a build past the release tag reports `0.3.17+<commits>.g<sha>` rather than understating itself as `0.3.17`. Emits `rerun-if-changed` for the git dir's `HEAD` and `logs/HEAD` plus the common dir's `packed-refs` and `refs/tags`, so cargo cannot serve a stale stamp. Degrades to the bare package version when git is absent (a tarball build).
- `build_version.rs` — the pure rendering/parsing of that string, `include!`d by `build.rs` and by `tests/cli.rs` (a build script cannot depend on its own crate)

## Session lifecycle

1. `launch` — starts Chrome via chromiumoxide with a fresh per-session user data directory (tempdir), saves session JSON to `~/.khora/sessions/<id>.json`. The Chrome PID is recorded so dead sessions can be detected.
2. Auto-reap — every non-`reap` CLI invocation calls `reap_stale_sessions()` first, which removes session files whose recorded PID is no longer running and deletes their data dirs. Best-effort; never fails the caller.
3. Subsequent commands — `load_and_verify()` loads the session file and re-checks the PID; if dead, the session file is removed and `KhoraError::SessionDead` is returned. Otherwise reconnects via `Browser::connect()` and calls `fetch_targets()` to discover existing tabs, both bounded by `--timeout`/`KHORA_TIMEOUT` so a wedged Chrome fails fast with `KhoraError::Timeout` instead of hanging.
4. `kill` / `reap` — closes the browser (if alive), removes the user data directory, and deletes the session file. If `connect()` times out (wedged but not confirmed dead), the PID is signaled directly (SIGTERM/SIGKILL) rather than treated as already-gone, since a `SessionDead` websocket refusal and a timed-out handshake mean different things — the resulting `Timeout` and `SessionDead` errors are handled by distinct match arms.

   The data-dir removal is `CdpClient::close()`'s job on the success arm, and an explicit `cleanup_data_dir()` call on the two error arms (which never get a client). That split is why `connect()` must carry the session's `data_dir` into the client rather than leaving it `None`: `kill`/`reap` *only* reach Chrome via `connect()`, so a `None` there makes `close()`'s cleanup a silent no-op and leaks the entire profile on the normal, healthy path while the failure paths clean up correctly (mesa task 574). Only `close()` acts on the field and only `kill`/`reap` call `close()`, so every other command's client holds the path and drops it harmlessly.

5. `reap --purge-data-dirs` — sweeps `khora-chrome-*` directories in the system temp dir that no current session record names, for profiles orphaned before the leak above was fixed. Directories modified within `PURGE_MIN_AGE` (60s) are spared: `launch` creates the data dir before it writes the session file, so a very fresh directory can belong to a session that is still starting up and would otherwise be invisible to the sweep.

Session files contain: ID, WebSocket URL, PID, headless flag, created-at timestamp, an optional `data_dir` path, and any emulation state that has to outlive a single CDP connection (`media`, `touch`, `viewport`, `keyboard` — see the emulation notes below). Every optional field is `#[serde(default)]` and skipped when absent, so session files written by older builds continue to load.

## CDP integration

Uses [chromiumoxide](https://crates.io/crates/chromiumoxide) (v0.9) for Chrome DevTools Protocol communication:

- **Launch**: `Browser::launch()` with platform-specific Chrome path
- **Reconnect**: `Browser::connect()` + `fetch_targets()` to discover existing pages, both wrapped in `tokio::time::timeout` so a wedged Chrome can't hang a command indefinitely
- **Navigate**: `page.goto(url)` (CDP `Page.navigate`) with a 10 s timeout; falls back to JS `window.location.href` + readyState polling when lifecycle events don't fire (common on reconnected sessions). `--no-cache` sends `Network.setCacheDisabled` first.
- **Element operations**: JavaScript evaluation via `page.evaluate()` for rich element info (`find`, `click`, `type`, `text`, `attribute`, `blur`, `wait-for`, `wait-gone`). `type` sets the value through the native React-tracked property setter so framework `onChange` handlers fire, then dispatches a synthetic `input` event. `blur` calls the element's native `blur()` so commit-on-blur handlers run without needing a trusted event.
- **Trusted input events**: `drag`, `mouse-down`, `mouse-move`, `mouse-up`, `click-at`, `dblclick-at`, `wheel`, `touch`, `swipe`, `pinch`, `long-press`, `key`, and `type-keys` bypass JS evaluation entirely and dispatch native, OS-trusted CDP input events (`Input.dispatchMouseEvent`, `Input.dispatchTouchEvent`, `Input.dispatchKeyEvent`) directly at viewport coordinates or as raw key codes. This is required for handlers gated on `event.isTrusted` or `setPointerCapture`, which synthetic JS/DOM events cannot satisfy — `wheel` specifically must be trusted because a synthetic `WheelEvent` never reaches Chromium's scroll pipeline at all, so it fires listeners without driving any actual scrolling or scroll chaining. `mouse-down`/`mouse-move`/`mouse-up` are separate CLI invocations that share no in-process state — persistence across the sequence works because Chrome's own input state (e.g. pointer capture) lives in the browser, not in khora.
- **Touch is a separate pipeline, not a mouse variant**: `touch-action` governs *touch* panning exclusively, so the trusted `wheel` above cannot exercise it and neither can a synthetic `TouchEvent` from `eval`. Each finger is a `TouchPoint` with a pinned id, so Chromium tracks it as one source across start/move/end; `touch`/`swipe`/`long-press` send one, and `pinch` sends two with distinct ids and an interpolated separation, which is what makes it a two-contact gesture rather than one finger teleporting. The dispatch commands themselves deliberately do **not** enable `Emulation.setTouchEmulationEnabled`: measurement showed dispatch, native panning and `pointerType` are identical either way, and Chrome reverts that override on disconnect — which khora does after every command — so an enable folded into a dispatch command would be gone before the next one could observe it. Making the page's *load-time feature detection* (`'ontouchstart' in window`, `navigator.maxTouchPoints`, `(pointer: coarse)`) report a touch device is a separate, session-persisted concern — see the touch-emulation bullet below. One serialization wrinkle: `touchEnd`/`touchCancel` must carry an empty `touchPoints`, but chromiumoxide's generated params skip the field when the vec is empty and CDP then rejects the call with `-32602`, so khora defines its own params type that always serializes it.
- **Compositor-frame nudge**: a page with no pending compositor frame — after a trusted key event consumes it, or on a never-painted page like a fresh `about:blank` tab — makes the next `mouseMoved` pay a ~5s hit-test tax and the next `mouseWheel` hang for chromiumoxide's full 30s internal timeout. `key_press` forces a cheap 1x1 screenshot after dispatch to fix the desync it causes; `drag`/`mouse-move`/`swipe`/`wheel` force one before their first dispatch to pre-warm a possibly-cold compositor, since that tax otherwise races khora's default 5000ms timeout. `wheel` was the last trusted-input method still dispatching into a possibly-cold compositor (mesa task 569) and is the one where it matters most, since `mouseWheel` has no fallback and hangs outright rather than degrading. Two honest caveats on the *preventive* half: only the `key_press` case was ever reproduced and root-caused live; neither the `mouse-move` tax (11 timed runs, task 386) nor the `wheel` hang (40 timed cold launches, task 569) reproduced against this repo's Chrome even with the fix absent, so those calls are defense-in-depth by analogy. The nudge costs ~30ms per call, measured on `wheel` (0.08-0.11s → 0.11-0.13s).
- **Console & network capture**: rather than subscribing to CDP events (which would need a long-lived listener khora doesn't have between invocations), `launch` injects JS shims that patch `console.log/warn/error/info` and `fetch`/`XMLHttpRequest`, buffering entries into `window.__khora_console` / `window.__khora_network`. The `console` and `network` commands read those buffers back out. Navigation replaces the page context and wipes them, so `navigate` reinstalls both hooks after load. Both installs are best-effort — a failure warns rather than failing the command.
- **Viewport**: `set-viewport` uses `Emulation.setDeviceMetricsOverride` to set arbitrary widths/heights (including phone widths headless Chrome rejects via `--window-size`), with `--mobile` toggling mobile emulation and `--reset` clearing the override via `Emulation.clearDeviceMetricsOverride`. Like media and touch emulation the override dies with the CDP connection, so it is persisted on the session (`SessionInfo::viewport`) and re-applied by `get_or_create_page()` on every connect, while `set-viewport` itself resolves the page without that re-apply so a new size doesn't first reflow the page at the old one. The loss it fixes is *staged*, which is why a one-shot command looked adequate for so long: the current document keeps rendering at the emulated width after the setting connection goes away, and only the next document created picks up the real window size. Measured, that next document is only created afresh on a **renderer-process swap** — a same-process navigation (`file://` → the same `file://`, same-origin `http://` → `http://`) kept the override even before it was persisted, while any cross-origin hop dropped it. A fresh `launch` sits on `chrome://new-tab-page/`, so the first navigate of every real run is a process swap and always lost it. `deviceScaleFactor` and `mobile` are weaker still — they were gone at the *first* disconnect, so before persistence `--mobile` never reached the command that consumed it, and a phone-width session was silently running non-mobile. That is also a visible behavior change now that it works: mobile emulation lays a page with no `<meta name="viewport">` out at Chrome's 980px default, exactly as a real phone would.
- **Media emulation**: `emulate-media` sets `Emulation.setEmulatedMedia` for `prefers-color-scheme`, `prefers-reduced-motion`, `forced-colors` and the media type. Unlike a device-metrics override, Chrome reverts this as soon as the CDP client that set it disconnects — which khora does after every command — so a one-shot call would be gone before the next invocation could observe it. The state is therefore persisted on the session (`SessionInfo::media`) and re-applied by `get_or_create_page()` on every connect; `emulate-media` itself resolves the page *without* that re-apply, so setting a new state doesn't first flip the page through the old one. The CDP call replaces the whole emulation state rather than adding to it, so the full desired state is sent every time and merging happens in the CLI. This is the only way to exercise a page's own `matchMedia` subscription: `matchMedia()` returns a fresh `MediaQueryList` per call, so a `change` event dispatched from `eval` never reaches the object the app registered on.
- **Touch emulation**: `emulate-touch` sets `Emulation.setTouchEmulationEnabled`, and follows the media-emulation shape for the same reason — Chrome reverts it on CDP disconnect, so the state lives on the session (`SessionInfo::touch`) and `get_or_create_page()` re-applies it on every connect, while `emulate-touch` itself resolves the page without that re-apply to avoid flipping `(pointer: coarse)` through the old value. The persistence is not merely convenience here: the re-apply runs *before* the navigation in the same invocation, which is the only way the override can reach a page's load-time feature detection. Measured, the signals do not move together — `navigator.maxTouchPoints` and the `pointer`/`hover` media queries change immediately, but `'ontouchstart' in window` is fixed when the document is created and so only follows on the next navigation. No device-metrics override is needed for the pointer queries; touch emulation alone moves them. This is orthogonal to the trusted `touch`/`swipe`/`long-press` dispatch, which is identical with and without emulation — what emulation changes is whether the app registered a handler in the first place.
- **On-screen-keyboard emulation**: `emulate-keyboard <px>` is the one `emulate-*` command with no CDP domain behind it — Chrome cannot raise a keyboard and the protocol models none. It shadows `window.visualViewport.height` with an own accessor over the one inherited from `VisualViewport.prototype`, returning the real getter's value minus the inset, and dispatches `resize` on that object. Reading the prototype descriptor on every install (rather than caching a "real" height) is what keeps it composable with `set-viewport` and makes re-installing idempotent; `--off` is a plain `delete`, which restores the genuine getter exactly. The layout viewport is deliberately untouched, and that asymmetry *is* the feature: a real mobile keyboard shrinks only the visual viewport, so `vh`/`dvh`/`%` and `position: fixed` keep reporting full height and a shell sized from them ends up behind the keyboard. `set-viewport` shrinks both, which makes the bug under test disappear into a green result — it is not a substitute. Unlike `matchMedia()`, which hands back a fresh `MediaQueryList` per call and so cannot be driven from injected JS, `window.visualViewport` is a **singleton**: the dispatched event reaches the very object the app subscribed to, which is why this needs no protocol support to be a real delivery. Persistence follows the touch-emulation shape (`SessionInfo::keyboard`, re-applied by `get_or_create_page()`), because the load-time half rides on `Page.addScriptToEvaluateOnNewDocument`, which is scoped to the CDP session and dies with it. **That registration only takes effect while the `Page` domain is enabled on the same session** — measured: without a preceding `Page.enable` Chrome accepts the call and silently never fires the script, so an app reading `visualViewport.height` at mount saw the full height while every post-load read looked correct, the most convincing possible false green. The enable therefore rides along with each re-apply; measured against a session with the keyboard on, it costs no extra `visualViewport` resize events. Not emulated, and stated rather than assumed: `visualViewport.offsetTop`, which a real browser makes non-zero when it scrolls the layout viewport to keep a focused input above the keyboard — nothing here is focused and nothing scrolls, so an `offsetTop`-based translate stays unverified after a green run.
- **Screenshot**: `Page.captureScreenshot` with `captureBeyondViewport`, always clipped explicitly — to the element's bounding box for `--selector` (resolved via `page.evaluate()`), to the user-supplied rectangle for `--clip X,Y,WxH`, or to `Page.getLayoutMetrics`' content size for a whole-page shot. `--clip` is the escape hatch for content the content size does not cover — a tall `position: fixed` overlay on a document pinned to `height: 100vh` contributes nothing to it, so a whole-page shot cuts the overlay off. Deliberately not chromiumoxide's `ScreenshotParams::full_page`, which captures whole pages by overriding device metrics to the content height and clearing the override afterwards: that reflows the page (`fixed`/`sticky`/`vh` layout renders at sizes the user never sees) and the trailing clear wipes any override `set-viewport` installed. Clipping touches no emulation state, so screenshots and `set-viewport` stay independent.
- **Page selection**: Prefers non-blank pages by CDP target URL, then falls back to JS `location.href` evaluation (handles stale target URLs after JS-based navigation). `find_page()` holds that policy and returns `None` when the browser has no page at all; `resolve_page()` is the thin wrapper that creates an `about:blank` tab in that case. The split exists so `targets` can ask which page khora *would* drive without the tab-creating side effect.
- **Target listing**: `targets` (alias `pages`) reports `Target.getTargets` minus the `browser` target, annotated with two independent flags — `driven` (the target `find_page()` picks) and `active` (`document.visibilityState === "visible"`, probed per page with a 1 s bound so a wedged renderer can't hang the listing that would diagnose it). CDP's `TargetInfo` carries no active flag and neither does `/json/list`, so the visibility probe is the only available signal. `driven` without `active` is the background-tab state behind mesa task 551, where trusted key dispatch keeps its modifier bits but loses `key`/`code`; the e2e suite and the key-wedge soak harness both assert on this command rather than scraping the DevTools HTTP port.

## Error handling

All errors flow through `KhoraError` with specific exit codes:
- 1: General error
- 2: Chrome not found
- 3: Timeout
- 4: Session not found or dead

## Output format

Two modes controlled by `--format` or `KHORA_FORMAT`:
- `text` — human-readable (default)
- `json` — structured JSON for agent consumption
